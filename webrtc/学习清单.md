# WebRTC 学习清单（基于 webrtcforthecurious.com）

**一句话主线**：两台机器要实时通话，需要依次解决 4 个问题——
怎么交换"我是谁、我能干什么"（信令/SDP）→ 怎么穿过 NAT 连上（ICE/STUN/TURN）→
怎么保证安全（DTLS/SRTP）→ 怎么在烂网络里把音视频和数据送过去（RTP/RTCP、拥塞控制、SCTP）。
整份清单分两层：第一层把 WebRTC 当黑箱学会用；实现细节层再沿这条主线打开黑箱。

**学习顺序（2026-10-14 调整）**：先学"第一层：功能与用法"，把 WebRTC 当黑箱用起来；
原来的第一遍、第二遍改为"实现细节层"，之后有时间再学，可以只读其中一部分。

**近期路线（2026-10-15 调整）**：目标是讲清"功能 + 怎么用"，不深入细节。合计约 2.5~3 天。

> **2026-10-16 顺序调整**：先学 4（拓展 E），再回到 2（B）、3（C），最后 5（F）。B1 已讲完，检查点还没做，回到 B 时先补 B1 的检查点。

### 1. A 能做什么 ✅ 已完成
WebRTC 的两层身份、四步流程、三种能力和五个卖点、9 个场景、5 种拓扑。

### 2. B 怎么用（约 1 天，学习模式三个阶段）
- **B1 核心 API 和四步的对应**（书 Ch1 API 一节）：把 API 按四步分组。
  - 采集：`getUserMedia` / `getDisplayMedia`（不属于连接对象）
  - 信令：`createOffer` / `createAnswer` / `setLocalDescription` / `setRemoteDescription`
  - 连接：`iceServers` 配置、`onicecandidate` / `addIceCandidate`、ICE 状态回调
  - 加密：**没有 API**，全自动完成；只能通过 `connectionstatechange` 知道"ICE 和 DTLS 都完成了"
  - 通信：`addTrack` / `ontrack`、`createDataChannel`
  - 检查点顺带补上 A 部分复述漏掉的 ③④
- **B2 信令的具体过程**（书 Ch2 两节 + MDN）：
  - 主叫方、被叫方的时序图；
  - 信令服务器转发的四种消息：offer、answer、候选、挂断；
  - 服务器只转发、不解读内容；
  - 候选是"找到一个就发一个"；
  - 消息顺序不能乱；
  - Transceiver 的收发方向（只讲一句）。
- **B3 一个完整应用由哪些部分组成**（MDN《Signaling and video calling》）：
  - 页面上的两个 video 元素、信令服务器、STUN/TURN 配置；
  - 摄像头权限：必须在 HTTPS 或 localhost 下，并且要用户授权；
  - 挂断与清理；
  - `getStats` 查看通话质量。
- **产出**（可直接放进学习文档）：一张两人通话时序图（标注每一步调用的 API 和经过的服务器），加一张"WebRTC 负责 / 你负责"职责分工表。
- **验收**：不看资料画出上面那张时序图。

### 3. C 动手（约半天，不从零写代码）

### 4. 拓展 E：横向对比（约半天~1 天，学习模式两个阶段）

## 第一层：功能与用法（约 2~4 天，优先）

> 这本书偏讲协议实现，用法层的内容只有第 1、2、8 章的一部分，所以要用 MDN 和官方示例补充。

### A. 它能做什么（约半天）
| 读什么 | 读完应能回答 |
|---|---|
| 书 Ch1 前半部分（What / Why、"a collection of technologies"） | WebRTC 由哪四个子系统组成？每个负责什么（一句话即可）？ |
| 书 Ch8 全章（应用场景和拓扑） | 一对一、多人会议、直播分别该用哪种拓扑？为什么多人会议通常要用 SFU 服务器？ |

三种核心能力：**音视频通话**（摄像头/麦克风采集 + 传输）、**屏幕共享**、**DataChannel**（传任意数据，比如文字、文件、游戏状态）。

### B. 怎么用（约 1~2 天）
| 读什么 | 读完应能回答 |
|---|---|
| 书 Ch1 "How does the WebRTC API work"（逐个 API 读一遍） | 建立一次连接时，API 的调用顺序是怎样的？ |
| 书 Ch2 只读"What is Signaling"和"Offers and Answers"两节，SDP 内容当黑箱 | 信令为什么要开发者自己做？Offer/Answer 是谁发给谁的？ |
| MDN《WebRTC API》总览，以及教程 *Signaling and video calling* | 一个完整的视频通话应用由哪几部分组成？ |

**重点要分清：哪些是 WebRTC 替你做的，哪些要你自己准备**：
- **WebRTC 替你做**：采集、编解码、穿过 NAT、加密、根据网络情况调整码率。
- **你自己准备**：
  - 信令服务器（通常用 WebSocket）
  - STUN/TURN 服务器（在 `iceServers` 里配置）
  - 多人场景下的 SFU 服务器
  - 房间、用户这些业务逻辑

需要掌握的 API 不多：
- `getUserMedia` / `getDisplayMedia`：采集摄像头、麦克风、屏幕
- `RTCPeerConnection`：建立连接
  - `createOffer` / `createAnswer`、`setLocalDescription` / `setRemoteDescription`：交换 Offer/Answer
  - `onicecandidate` / `addIceCandidate`：交换网络候选
  - `addTrack` / `ontrack`：发送和接收音视频
  - `connectionstatechange`：监听连接状态
- `createDataChannel`：建立数据通道
- `getStats`：查看连接质量

### C. 动手（约 1~2 天，这一层的主体）
> **近期精简版（约半天）**：只做第 1 步，以及官方 samples 里的 DataChannel 示例，全程开着 webrtc-internals。
> 第 2~5 步留到之后。

按顺序做，每一步都在上一步的基础上加东西：
1. **单页面回环**：同一个页面里建两个 `RTCPeerConnection`，自己连自己（参考官方 webrtc samples 里的 pc1 示例）——先看清调用顺序。
2. **两个标签页手动交换 SDP**：复制粘贴 Offer/Answer，体会"信令"到底在传什么。
3. **加一个最小的 WebSocket 信令服务器**，让两台电脑视频通话（局域网能通之后，再试试跨网络，体会为什么需要 STUN/TURN）。
4. **DataChannel**：在上面的基础上加文字聊天或文件传输。
5. （可选）**浏览器之外**：用 Python 的 aiortc 写一端，和浏览器通话——验证"WebRTC 是协议，不是浏览器专属"。

全程打开 `chrome://webrtc-internals` 观察，现在不求看懂，混个眼熟就行。

### 第一层验收
- 能独立写出一个两人视频通话 + 文字聊天的小应用；
- 能说清 WebRTC 替你做了什么、你要自己准备什么；
- 能为一个给定场景（比如 1 对 1 客服、20 人网课、远程操控机器人）选出拓扑和需要的服务器。

## 细节第二遍：细读——讲清每个环节"为什么这样设计"（约 6~9 天）

按"承重程度"排序，前 4 项是重点：

1. **Ch3 NAT 与 ICE 细节**（重点）：映射行为 × 过滤行为的组合，以及哪些组合打洞会失败；STUN 怎样拿到公网地址；TURN 的 Allocation/Permission；ICE 的连通性检查与候选选择、ICE Restart。
2. **Ch6 RTP/RTCP 逐字段 + 拥塞控制**（重点）：Sequence Number、Timestamp、SSRC、Marker、Payload Type 各自的作用；SR/RR、NACK、PLI/FIR；**TWCC + GCC**（基于延迟梯度的带宽估计）。
3. **Ch4 DTLS 握手与密钥导出**（重点）：握手状态机走一遍、fingerprint 和证书怎样对上、密钥怎样从 DTLS 导出给 SRTP 使用。
4. **Ch2 SDP 关键字段**（重点）：BUNDLE、mid、ice-ufrag/pwd、rtpmap/fmtp、setup、ssrc——对照一份真实 SDP 逐行读。
5. **Ch5 回看**：带着第 6 章的机制回来重读，把"问题 → 机制"一一对上（丢包 → NACK/FEC，抖动 → JitterBuffer，拥塞 → GCC）。
6. **Ch7 SCTP 浅读**：Association/Stream、TSN、FORWARD TSN（不可靠模式就是靠它实现的）；DCEP 两个消息看懂即可。
7. **Ch9 Debugging**：结合 webrtc-internals / Wireshark 抓一次包，亲眼看到 STUN → DTLS → SRTP 的顺序。

**第二遍仍可忽略**：mDNS 候选细节、TMMBR/TMMBN、带宽估计的其他方案、SCTP 的 ERROR/ABORT/SHUTDOWN chunk、DCEP 字段、History。

**第二遍验收**：
- 给一份真实 SDP，能逐行说清每行在干什么；
- 给一个"连不上"的场景（例如双方都是对称型 NAT），能说出卡在哪一步、怎么解决；
- 用 Wireshark 抓包能认出 STUN / DTLS / RTP / RTCP 四类报文。
